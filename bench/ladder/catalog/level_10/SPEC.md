# Extend the helpdesk: audit log, severity, labels and merge

The code directory contains `helpdesk/`, an existing, working ticketing system of about 2,000 lines (read `README.md` first; its unit tests are in `tests/` and run with `python3 -m unittest discover -s tests`).
Make the changes below. They touch many modules and must fit the existing design: services take an `actor_id`, every change ends with one `store.save()`, the clock is injected, the data file is one JSON document.
Python 3, standard library only, no network. Independent tests use the Python API and the command line (`python3 -m helpdesk`).

**Compatibility is part of the task.** Everything that worked before must keep working: all existing unit tests keep passing unmodified; existing public names, signatures, keyword arguments and return types keep working; existing command line commands keep their output and exit statuses (new output lines may only be added after the existing ones); data files written by the old version (version 1) must still open; files read by other tools (CSV and JSON exports) keep their existing columns and keys in the same order (new ones may only be appended).

## Requirements

1. Audit log. Add the module `helpdesk/audit.py` with the class `AuditLog(store, clock)`. Entries are dicts with exactly the keys `seq`, `ts`, `actor`, `action`, `entity`, `entity_id`, `outcome`, `changes`, `reason`: `seq` counts 1, 2, 3, ... over the whole log, `ts` comes from the clock, `actor` is the acting user's id (or `None` for system or bootstrap actions), `outcome` is `"ok"` or `"denied"`, `changes` maps a field name to `[old, new]`, and `reason` is `None` unless the outcome is `denied`. `record(actor, action, entity, entity_id, changes=None, outcome="ok", reason=None)` appends and returns an entry; `entries(entity=None, entity_id=None, actor=None, action=None, outcome=None, since=None)` returns copies of the matching entries in `seq` order (`since` is an inclusive ISO timestamp); `count_by_action()` returns a dict of counts sorted by action name. The log lives in the data file under the key `"audit"` and is written by the same atomic save as the change it describes (never a change without its entry, never an entry without its change). `Helpdesk` exposes it as `hd.audit`, and `Store` keeps the entries in `store.audit`.

2. What is audited. Every successful operation that changes something appends exactly one entry, with `entity` `"user"` or `"ticket"` and the id of the affected object. Actions and `changes`: `user.create` `{"name": [None, name], "role": [None, role]}`, `user.disable` `{"active": [True, False]}`, `user.role` `{"role": [old, new]}`; `ticket.create` `{"title": [None, title], "severity": [None, severity], "category": [None, category], "requester_id": [None, requester id]}`; `ticket.assign` `{"assignee_id": [old, new]}` plus `"status": [old, new]` when the assignment also moved the ticket from open to in progress; `ticket.status` `{"status": [old, new]}` plus `"resolution": [old, new]` when the resolution text changed; `ticket.severity` `{"severity": [old, new]}`; `ticket.comment` `{"comment_id": [None, id], "internal": [None, bool]}`; `ticket.watch` and `ticket.unwatch` `{"watchers": [old list, new list]}`; `ticket.attach` `{"attachments": [count before, count after]}`; `ticket.label_add` and `ticket.label_remove` `{"labels": [old list, new list]}`; `ticket.link` and `ticket.unlink` `{"links": [count before, count after]}`; `ticket.merge` (see 6); `ticket.purge`, one entry per purged ticket, `{"status": [status, None]}`. `UserService.create_user` gets the optional parameter `actor_id=None`: when given, the actor needs the `manage_users` permission and is recorded as `actor`; without it nobody is asked and `actor` is `None`. Operations that go through the services (bulk, escalation, rules, import, templates, balancer) are audited because the services are. Calls that change nothing (watching twice, adding a label the ticket already has, setting the severity it already has, `disable` of a disabled user) create no entry. A call that fails with `PermissionDenied` creates one entry with outcome `"denied"`, `changes` `{}`, `reason` the exception message, `actor` the acting user, the same `action` name the successful call would have had (`ticket.assign` for a refused assignment, `ticket.create`, `ticket.status`, `ticket.comment` for a refused internal note, `user.disable`, `ticket.purge` with `entity_id` `None`, and so on) and `entity_id` the targeted object (`None` when there is none), and it is saved before the exception propagates. Validation errors, unknown ids and invalid transitions create no entry.

3. Severity (data model change). The priority scale gets new names, stored as the ticket field `severity`: `low`, `medium`, `high`, `critical`, corresponding to the old priorities `low`, `normal`, `high`, `urgent`. `config.SEVERITIES`, `config.PRIORITY_TO_SEVERITY` and `config.SEVERITY_TO_PRIORITY` (a dict each way) are added; `config.PRIORITIES` and `config.SLA_HOURS` stay as they are (a `sla_hours` override in the settings file affects both vocabularies). `Ticket` keeps working with the old vocabulary: `ticket.priority` returns the old name of the severity and assigning an old name changes the severity; `Ticket(..., priority=...)` is still accepted in its old position next to the new keyword `severity=` (giving both with different meanings is a `ValueError`); the default is `medium`/`normal`. `Ticket.to_dict()` is the stored form: it contains `severity` and no `priority`; `Ticket.from_dict` accepts both. `TicketService.create(requester_id, title, description, priority="normal", category="general", actor_id=None, severity=None)` accepts either vocabulary (`severity` wins when `priority` is left at its default; an explicit non-default `priority` that contradicts `severity` is a `ValidationError`); `set_priority(ticket_id, priority, actor_id)` keeps taking old names and the new `set_severity(ticket_id, severity, actor_id)` takes new names, both write the audit action `ticket.severity` and both recompute `sla_due` from the creation time; `list(...)` gets the keyword filters `severity=` and `label=` next to `priority=`. The SLA deadline is still derived from the same hours (critical 4, high 8, medium 24, low 72); `sla.due_for_severity(severity, created)` and `sla.hours_for_severity(severity)` are added to `helpdesk/sla.py`. The search language accepts `severity:medium` next to `priority:normal` (both filters work on every ticket); `reports.summary` keeps `by_priority` (old names) and adds `by_severity` and `by_label`; `escalation` keeps reporting old priority names. The CSV export appends the columns `severity`, `labels` (joined with `|`) and `merged_into` (empty when none) after the existing ten; the JSON export keeps `priority` (old names) in every ticket and adds `severity`, `labels` and `merged_into`.

4. Data file version 2. The file format version becomes 2 (`store.VERSION == 2`). A version 1 file is migrated when it is opened: every ticket's `priority` becomes `severity` (`normal` becomes `medium`, `urgent` becomes `critical`, the others keep their name) and the key `priority` is removed, every ticket gets `"labels": []` and `"merged_into": null`, everything else is kept exactly, the audit log is created with one entry (`seq` 1, `actor` `None`, `action` `"store.migrate"`, `entity` `"store"`, `entity_id` `None`, `outcome` `"ok"`, `changes` `{"version": [1, 2]}`) stamped with the clock, the original file is kept untouched as `<data file>.v1.bak`, and the migrated document is written at once as version 2. `Store(path, clock=None)` gets the optional clock for that stamp. Opening a version 2 file migrates nothing and creates no backup; a version above 2 still raises `StoreError` (whose message names the unsupported version); a damaged file still raises `StoreError`. Tickets keep all their other data (comments, watchers, attachments, links, notifications, saved searches, counters) through the migration.

5. Labels. `TicketService.add_label(ticket_id, label, actor_id)` and `remove_label(ticket_id, label, actor_id)` (both return the ticket) manage the new ticket field `labels` (a list in the order added). A label is lowercased and matches `[a-z0-9][a-z0-9-]{0,23}` (otherwise `ValidationError`), a ticket has at most `config.MAX_LABELS == 8` labels (`ValidationError`), adding an existing label does nothing, removing a label the ticket does not have raises `NotFound`. Only roles with the new permission `label` (admin and agent) may do it; customers get `PermissionDenied`. The search language gets `label:name`, which may be repeated: all given labels are required (`parse_query("label:a label:b").filters["label"] == ["a", "b"]`). `TicketService.list(..., label=)` filters by label. `reports.summary` has `by_label`, the number of tickets per label. The command line gets `ticket label add ID LABEL` and `ticket label remove ID LABEL` (both print `Ticket #N labels: a, b`, or `-` when none are left), `ticket list --label L` and `ticket list --severity S`, `ticket severity ID S`, `ticket add ... --severity S`; and `ticket show` prints the new lines `Severity: ...`, `Labels: a, b` (only if there are labels) and `Merged into: #N` (only if merged) after the existing header lines and the `Resolution:` line, before the link lines.

6. Merge. `TicketService.merge(source_id, target_id, actor_id)` merges a duplicate ticket into another and returns the number of comments moved. Only roles with the new permission `merge` (admin and agent) may do it. Errors (all `ValidationError`, nothing changes): source equals target; the source is closed (the message mentions `merged into #N` if it was merged earlier); the target was itself merged into another ticket; the target is closed. Effects: the source's comments move to the target (keeping their ids and timestamps, with `ticket_id` updated) and the target's comments are then ordered by `(ts, id)`; the source's labels that the target lacks are added to the target while it has room; the source's watchers are added to the target's watchers; links of OTHER tickets that pointed to the source now point to the target (a link is never duplicated); links of the source and links between the two are dropped; the source becomes `closed` with `closed_at` set to now, `resolution` `"merged into #T"`, `merged_into` the target's id, and no comments; both tickets' `updated` become now; the source's assignee, if there is one and it is not the actor, gets a notification of kind `status` with the message `ticket #S was merged into #T`. It writes one audit entry, action `ticket.merge`, entity `ticket`, entity id the SOURCE, `changes` `{"merged_into": [None, T], "status": [old status, "closed"], "comments_moved": [0, n]}`. The command line gets `ticket merge SOURCE TARGET`, printing `Merged ticket #S into #T (N comment(s) moved)`.

7. Reading the audit log. The command line gets `audit list [--entity E] [--id N] [--actor U] [--action A] [--outcome O] [--limit N]`, which needs the new permission `audit` (admins only; others get `PermissionDenied`, exit status 3) and prints one line per matching entry in `seq` order: `#SEQ TS actor=ID ACTION ENTITY:ID OUTCOME`, with `-` for a missing actor or entity id (for example `#12 2024-03-01T09:00:00 actor=2 ticket.assign ticket:5 ok`); `--limit N` keeps the last N matches; no match prints `No audit entries.`. `report audit` prints one `ACTION: COUNT` line per action sorted by action (`The audit log is empty.` when there is none). `helpdesk/timeline.py` also shows what the audit log knows about the ticket, as additional rows. The timeline is built in this order: the existing rows (creation, comments, attachments, closing), then the audit rows in log order, and then sorted by timestamp with a stable sort (so rows with equal timestamps keep that order). The audit rows are: `assigned to NAME by ACTOR`, `status changed from X to Y by ACTOR` (but NOT for a change to `closed`, which the timeline already shows from `closed_at`), `severity changed from X to Y by ACTOR`, `label L added by ACTOR`, `label L removed by ACTOR` and `merged into #T by ACTOR`; an actor of `None` is shown as `system`. `housekeeping.check_integrity` additionally reports a `merged_into` that points to a missing ticket (`ticket #N: merged into missing ticket #M`) and an audit log whose `seq` numbers are not 1, 2, 3, ... (`audit entry K: sequence number is X`, reported once).
