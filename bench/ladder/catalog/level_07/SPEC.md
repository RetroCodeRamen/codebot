# SQLite inventory system

Build `inventory.py` in the root of the code directory: an inventory system for a small shop on top of SQLite (`sqlite3` from the standard library). Python 3, no third-party packages, no network.
Products, stock movements, reservations and transactions must stay consistent, the database file must be upgraded from older versions of its schema, and every operation is all-or-nothing.
The module's public interface is exactly the one described here; independent tests create databases (including old-format ones) and call it.

## Requirements

1. Schema and migrations. `Inventory(path=":memory:", clock=None)` opens (and creates if needed) the SQLite database at `path`, enables foreign keys, and upgrades the schema to the latest version, which is `Inventory.SCHEMA_VERSION == 3`. The schema version is stored in `PRAGMA user_version` and returned by `schema_version()`. Version 1 is: `CREATE TABLE products(sku TEXT PRIMARY KEY, name TEXT NOT NULL, price_cents INTEGER NOT NULL CHECK(price_cents >= 0), stock INTEGER NOT NULL DEFAULT 0 CHECK(stock >= 0))` and `CREATE TABLE movements(id INTEGER PRIMARY KEY AUTOINCREMENT, sku TEXT NOT NULL REFERENCES products(sku), delta INTEGER NOT NULL, reason TEXT NOT NULL, ref TEXT, ts TEXT NOT NULL)`. Version 2 adds `CREATE TABLE reservations(id INTEGER PRIMARY KEY AUTOINCREMENT, order_ref TEXT NOT NULL, sku TEXT NOT NULL REFERENCES products(sku), qty INTEGER NOT NULL CHECK(qty > 0), state TEXT NOT NULL DEFAULT 'active' CHECK(state IN ('active', 'released', 'fulfilled')), ts TEXT NOT NULL)`. Version 3 adds the column `reorder_level INTEGER NOT NULL DEFAULT 0 CHECK(reorder_level >= 0)` to `products` and an index on `movements(sku)`. A new empty database gets all three steps. A database at version 1 or 2 (it may contain data) is upgraded in place when opened, keeping every row; each step runs in its own transaction, so a failing step leaves the database at the previous version. A database with a version higher than 3 raises `SchemaError` and is not modified. `close()` closes the connection and the object works as a context manager. `clock` is a function returning the current time as a string; the default returns the local time as `YYYY-MM-DDTHH:MM:SS`.

2. Products. The module defines the exception classes `InventoryError(Exception)`, `DuplicateSku`, `UnknownSku`, `UnknownOrder`, `InsufficientStock` and `SchemaError`, all subclasses of `InventoryError`, and the dataclasses `Product(sku, name, price_cents, stock, reorder_level)`, `Movement(id, sku, delta, reason, ref, ts)` and `Reservation(id, order_ref, sku, qty, state, ts)`. `add_product(sku, name, price_cents, reorder_level=0)` creates a product with stock 0 and returns the `Product`; `sku` and `name` are stripped and must be non-empty strings, `price_cents` and `reorder_level` must be integers (a `bool` is not an integer) and not negative, otherwise `ValueError`; an existing sku raises `DuplicateSku`. `get_product(sku)` returns the product or raises `UnknownSku`; `list_products()` returns all products sorted by sku.

3. Stock movements. `receive(sku, qty, ref=None)` adds `qty` (an integer of at least 1, else `ValueError`) to the stock, records a movement with reason `"receive"` and returns the new stock. `adjust(sku, delta, reason)` changes the stock by a non-zero integer `delta` with a non-empty `reason` (else `ValueError`), records the movement and returns the new stock; the stock may never become negative and may never drop below the quantity reserved for open orders: both raise `InsufficientStock` and change nothing. `stock(sku)` returns the current stock, `history(sku)` returns the product's movements as `Movement` objects in the order they happened (`delta` is signed, `ts` comes from the clock, `ref` is `None` when not given). Every stock change, and nothing else, creates exactly one movement. An unknown sku raises `UnknownSku` in all of these.

4. Reservations. `reserve(order_ref, sku, qty)` reserves `qty` units (integer of at least 1) for an order, creates a reservation in state `"active"` and returns it; it raises `InsufficientStock` if fewer than `qty` units are available. `available(sku)` is the stock minus the quantity of the sku's active reservations. Reserving does not change the stock or create movements. `release(order_ref)` sets every active reservation of that order to `"released"` and returns how many there were. `fulfill(order_ref)` sets every active reservation of that order to `"fulfilled"`, and for each of them removes the quantity from the stock with a movement of reason `"sale"`, `ref` equal to the order reference and a negative `delta`; it returns the list of the created movements in reservation order. Both raise `UnknownOrder` if the order has no active reservation, and both are atomic. `reservations(order_ref=None, state=None)` returns the matching reservations ordered by id.

5. Transactions. Every public operation is atomic: if it fails with any exception, the database is exactly as it was before the call. `batch(ops)` runs a list of operations in ONE transaction and returns the list of their results; if any operation fails, none of them has any effect and the exception is raised. An operation is a tuple whose first element names the method: `("add_product", sku, name, price_cents[, reorder_level])`, `("receive", sku, qty[, ref])`, `("adjust", sku, delta, reason)`, `("reserve", order_ref, sku, qty)`, `("release", order_ref)`, `("fulfill", order_ref)`. An unknown operation name raises `ValueError` (and nothing is applied). Later operations of a batch see the effects of earlier ones.

6. Consistency. `verify()` returns a list of problem descriptions (empty when everything is consistent): `stock mismatch for SKU: cached X, movements Y` for every product whose stored stock differs from the sum of its movements, and `over-reserved SKU: reserved R, stock S` for every product whose active reservations exceed its stock; products are reported in sku order, mismatches before over-reservations. `repair()` sets the stored stock of every mismatching product to the sum of its movements, in one transaction, and returns how many products it fixed; it does not change movements or reservations.

7. Reports. `low_stock()` returns the sorted list of skus that have a `reorder_level` above 0 and whose available quantity is at or below that level. `stock_value()` returns the total value in cents, the sum over all products of stock times price.

8. Persistence and concurrency. Data written through one `Inventory` object is visible to another object opened on the same file as soon as the operation returns, and survives closing and reopening. Several threads or processes may use their own `Inventory` object on the same file at once without losing updates or overselling: writers wait for each other (a busy timeout of at least 30 seconds) and every read-modify-write sequence of an operation runs inside a write transaction (`BEGIN IMMEDIATE`). With 5 units in stock and 12 concurrent `reserve` calls for 1 unit each, exactly 5 succeed and 7 raise `InsufficientStock`. A single `Inventory` object may also be shared between threads.
