# Local inventory REST API

Build `inv_api.py` in the root of the code directory: a JSON REST API for a small product inventory, served over HTTP on the local machine, with SQLite persistence.
Python 3, standard library only (`http.server`, `sqlite3`, `json`, `threading`), no network access beyond binding a local port. Independent tests start the server on a free port and talk to it over HTTP.
All request and response bodies are JSON and every response (also errors) carries `Content-Type: application/json` and a correct `Content-Length`; error responses have the form `{"error": "<message>"}`.

## Requirements

1. Server lifecycle. `make_server(db_path, tokens, host="127.0.0.1", port=0)` creates the database tables if they do not exist and returns a server object with the attribute `port` (the real port, also when `port=0` was given), `start()` (serve in a background daemon thread; returns the server), `stop()` (stop serving and release the port) and the context-manager protocol (`with make_server(...) as s:` starts it and stops it on exit). `tokens` maps API tokens (non-empty strings) to roles, `"admin"` or `"reader"`; any other role raises `ValueError`. The server handles requests in parallel (one thread per request). `GET /health` returns `200 {"status": "ok"}` and needs no authentication.

2. Authentication and roles. Every other request needs the header `Authorization: Bearer <token>` with a configured token; otherwise the response is `401 {"error": "unauthorized"}` with the header `WWW-Authenticate: Bearer`. A `reader` may only use `GET` requests; any other method from a reader is `403 {"error": "forbidden"}`; an `admin` may do everything. The checks happen in this order: unknown path `404 {"error": "not found"}`; (health is open); authentication 401; method not allowed for that path `405 {"error": "method not allowed"}` with an `Allow` header listing the allowed methods sorted and joined by `", "`; role 403; request body 400/413; validation 422; existence 404; conflicts 409.

3. Creating and reading products. `POST /products` with `{"sku", "name", "price_cents", "reorder_level"}` (the last is optional, default 0) creates a product with stock 0 and answers `201` with the product `{"sku", "name", "price_cents", "reorder_level", "stock"}` and the header `Location: /products/<sku>`. Validation: `sku` is a string of 1 to 32 characters from `A-Z a-z 0-9 . _ -`; `name` is a string that is not empty after stripping (the stored name is stripped) and at most 100 characters; `price_cents` and `reorder_level` are non-negative integers (a JSON `true` is not an integer); any other field is unknown. Invalid input answers `422 {"error": "validation failed", "fields": {"<field>": "<message>"}}` listing every invalid field (a missing required field counts, and an unknown field is reported with the message `unknown field`). An existing sku answers `409 {"error": "sku already exists"}`. `GET /products/<sku>` returns the product or `404 {"error": "not found"}`.

4. Updating and deleting. `PATCH /products/<sku>` takes an object with any of `name`, `price_cents`, `reorder_level` (same validation as above; `sku` and `stock` cannot be patched and are unknown fields) and answers `200` with the updated product; an empty object is `400 {"error": "nothing to update"}`. `DELETE /products/<sku>` answers `204` with an empty body and removes the product and its movements, but only if its stock is 0; otherwise `409 {"error": "product still has stock"}`. Unknown skus are `404`.

5. Listing, filtering and pagination. `GET /products?limit=L&offset=O&q=TEXT` returns `{"items": [products sorted by sku], "total": N, "limit": L, "offset": O}`. `limit` defaults to 20 and must be an integer from 1 to 100, `offset` defaults to 0 and must be a non-negative integer; otherwise `400 {"error": "invalid limit"}` or `400 {"error": "invalid offset"}` (limit is checked first). `q` keeps only products whose sku or name contains the text, ignoring case (an empty `q` keeps everything); `total` counts the matches before pagination and `limit`/`offset` echo the values used. An offset beyond the end gives an empty `items` list.

6. Stock and movements. `POST /products/<sku>/stock` with `{"delta": <non-zero integer>, "reason": <non-empty string>}` changes the stock and answers `200 {"sku": ..., "stock": <new stock>, "movement_id": <int>}`; invalid or unknown fields are `422` with `fields` as in requirement 3; a change that would make the stock negative is `409 {"error": "insufficient stock"}` and changes nothing. `GET /products/<sku>/movements?limit=L&offset=O` lists that product's movements oldest first as `{"id", "delta", "reason", "ts"}` objects in the same pagination envelope as requirement 5 (`ts` is a `YYYY-MM-DDTHH:MM:SS` string); an unknown sku is 404.

7. Protocol details. A request body for `POST` or `PATCH` that is not valid JSON, or not a JSON object, is `400 {"error": "invalid JSON"}` respectively `400 {"error": "body must be a JSON object"}`; a body larger than 1048576 bytes (checked from `Content-Length`, before reading it) is `413 {"error": "request too large"}`. A missing body counts as invalid JSON for `POST` and `PATCH`. Unknown paths are 404, and a known path with an unsupported method is 405 (for example `DELETE /products`, `PUT /products/x`, `GET /products/x/stock`). The server keeps connections alive (HTTP/1.1) and never prints request logs to the console.

8. Persistence and consistency. All data lives in the SQLite file `db_path`: after `stop()` a new server on the same file serves exactly the same data, including all movements with their ids. Concurrent requests are safe: 20 concurrent `POST .../stock` requests of `+1` on one product end with stock 20 and 20 movements; with stock 5, 12 concurrent requests of `-1` give exactly 5 `200` and 7 `409` answers. Stock changes are atomic (the stock and its movement are written together or not at all).
