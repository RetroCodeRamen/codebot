# Local issue tracker

Build the Python package `tracker/` in the code directory: a complete local issue tracker with users and permissions, projects, issues with comments and labels, search, audit logging, SQLite persistence, a local HTTP API, import and export, and background maintenance.
Python 3, standard library only, no network access beyond binding a local port. This is a large project: plan it as many small tasks and keep the modules separate (suggested layout: `tracker/core.py` with the `Tracker` class, `tracker/search.py`, `tracker/api.py`, `tracker/maintenance.py`, and `tracker/__init__.py` exporting the public names). Independent tests use the Python API and the HTTP API.
All timestamps are strings `YYYY-MM-DDTHH:MM:SS` from the injected clock (default: local time). `actor` arguments are user NAMES (strings).

## Requirements

1. Package and persistence. `tracker/__init__.py` exports `Tracker`, `Maintenance` and the exception classes `TrackerError`, `AuthError`, `PermissionDenied`, `NotFound`, `ValidationError` (also a `ValueError`) and `Conflict`, all except `ValidationError`'s extra base subclasses of `TrackerError(Exception)`. `Tracker(path=":memory:", clock=None)` opens or creates the SQLite database `path` (foreign keys on, writers wait for each other for at least 30 seconds, every operation is atomic: when it fails nothing is changed), supports `close()` and the context-manager protocol, and can be used from several threads. Everything survives closing and reopening the file.

2. Users. `create_user(name, password, role="member", actor=None)` returns `{"id", "name", "role", "active", "created"}`. Names have 2 to 30 characters from letters, digits, `.`, `_`, `-` and start with a letter, are unique ignoring case, and keep the spelling given; the password has at least 8 characters and is never stored in clear text; roles are `admin`, `member`, `viewer` (`ValidationError` for anything invalid, `Conflict` for an existing name). The very first user must be an admin and needs no actor; afterwards an active admin must be named as `actor`, otherwise `PermissionDenied`. `get_user(name)` (unknown: `NotFound`); `list_users(actor)` lists all users by id for any active actor; `set_active(name, active, actor)` (admins only) disables or enables an account and deletes the tokens of a disabled user. A disabled user can neither log in nor act: every operation naming them as actor raises `PermissionDenied`.

3. Authentication. `login(name, password)` returns a random token (a string of at least 32 characters) valid for 24 hours of clock time; wrong name, wrong password or a disabled account raise `AuthError("invalid credentials")` (the same for all three). `authenticate_token(token)` returns the user dict or raises `AuthError`; `logout(token)` invalidates it. Passwords are verified with a salted, slow hash (for example PBKDF2) and compared in constant time.

4. Projects. `create_project(key, name, actor, public=False)` (admins only) returns `{"key", "name", "public", "archived", "created"}`; keys are 2 to 10 characters, capital letters and digits, starting with a letter; names 1 to 100 characters; an existing key is a `Conflict`. A PUBLIC project is visible to every active user, a private one only to its members and to admins; whoever cannot see a project (or an issue or comment in it) gets `NotFound` from every operation on it, read or write. `get_project(key, actor)` and `list_projects(actor)` (sorted by key, only visible projects) return the same dicts. `add_member(key, user_name, role, actor)` sets the project role `manager`, `developer` or `reporter` of a user (a second call changes the role; returns `{"user", "role"}`), `remove_member(key, user_name, actor)` (`NotFound` if the user is no member) and `members(key, actor)` (sorted by name) need the manager role or an admin. `archive_project(key, actor)` (admins only) makes the project read-only: every write to it, also by admins, is `PermissionDenied`.

5. Permissions. Admins may do everything on a visible project except write to an archived one. Users with the global role `viewer` can never write. Everyone else acts through their project role: a `manager` may do everything in the project (create, edit, assign, transition, comment, label, delete any comment, manage members, export); a `developer` may create issues, edit any issue's title and description and priority, assign, transition, comment, edit and delete own comments and label; a `reporter` may create issues, edit the title and description of issues they reported, comment and edit or delete their own comments, and nothing else. Members of a public project who have no project role, and visitors, may only read. A refused operation raises `PermissionDenied` with a message that names the actor and what was refused.

6. Issues. `create_issue(project, title, description="", actor=None, priority="medium", assignee=None, labels=())` returns the issue dict `{"key", "project", "number", "title", "description", "status", "priority", "reporter", "assignee", "resolution", "created", "updated", "closed", "labels"}`. Numbers count 1, 2, 3, ... per project and form the key `KEY-N`, never repeating, also under concurrent creation from several threads or processes. Title: 1 to 200 characters after stripping; description at most 20000 characters; priorities `low`, `medium`, `high`, `critical`; the reporter is the actor; an assignee (a user name who can at least comment in the project) needs the `assign` right; labels need the `label` right and follow requirement 8. `get_issue(issue_key, actor)` returns the same dict plus `"comments"` (a list of `{"id", "author", "body", "created", "edited"}` in id order). `update_issue(issue_key, actor, **fields)` accepts `title`, `description`, `priority` and `assignee` (a name or `None`), returns the updated dict, ignores values that do not change anything, and sets `updated` only when something changed; other field names are a `ValidationError`; `priority` needs the right to edit any issue, `assignee` the right to assign, `title` and `description` the right to edit any issue or to edit an own issue. `transition(issue_key, status, actor, resolution=None)` follows `open -> in_progress | resolved | closed`, `in_progress -> open | resolved | closed`, `resolved -> open | closed`, `closed -> open`; any other change is a `ValidationError`; `resolved` needs a non-empty `resolution`, which is stored (stripped) and cleared when the issue is reopened; `closed` sets `closed` to now and leaving `closed` clears it. Unknown issue keys are `NotFound`.

7. Comments. `add_comment(issue_key, body, actor)` returns `{"id", "author", "body", "created", "edited"}` (`edited` is `None`; the body is 1 to 20000 characters after stripping) and sets the issue's `updated`; `edit_comment(comment_id, body, actor)` is allowed for the author only (also a manager may not edit others' comments), stores the new body and the edit time in `edited` and returns `{"id", "body"}`; `delete_comment(comment_id, actor)` is allowed for the author and for managers and admins. Rights follow requirement 5.

8. Labels. A label is lowercased and matches `[a-z0-9][a-z0-9-]{0,29}` (else `ValidationError`); an issue has at most 10. `add_label(issue_key, label, actor)` and `remove_label(issue_key, label, actor)` return the updated issue dict; adding a label the issue already has does nothing (and does not touch `updated`), removing a label it does not have is a `NotFound`; both need the `label` right (manager, developer, admin).

9. Search. `search(query="", actor=None, limit=20, offset=0, sort="-updated")` returns `{"items": [issue dicts without comments], "total": n, "limit": limit, "offset": offset}` over the issues in projects the actor can see. The query is a space separated list of `field:value` filters and plain words: `project:KEY`, `status:open,in_progress` (several values allowed), `priority:high,critical`, `assignee:alice` or `assignee:none`, `reporter:bob`, `label:bug` (repeatable, all required) and words (each must occur, ignoring case, in the title or the description). Names compare ignoring case. An unknown field, an empty value or an unknown `sort` is a `ValidationError`; `limit` is an integer from 1 to 100 and `offset` a non-negative integer (`ValidationError` otherwise). `sort` is `created`, `updated`, `priority` (critical highest) or `number`, with a leading `-` for descending; ties are broken by the internal issue id in the same direction. `total` counts all matches before paging. `project_stats(key, actor)` returns `{"project", "total", "by_status", "by_priority", "by_assignee" (unassigned counted under "-"), "by_label"}`, each breakdown a dict sorted by key.

10. Audit log. The table `audit` records, in the same transaction as the change, one entry for every successful change, and one with outcome `denied` for every refused operation (also failed logins). `audit_entries(actor, action=None, entity=None, entity_id=None, who=None, outcome=None, since=None, limit=None)` (admins only, else `PermissionDenied`) returns dicts `{"seq", "ts", "actor", "action", "entity", "entity_id", "outcome", "changes", "reason"}` in `seq` order (`seq` counts 1, 2, 3, ... without gaps; `entity_id` is always a string or `None`; `changes` maps field names to `[old, new]`; `reason` is set for denied entries; `limit` keeps the last N). Actions and entities: `user.create` (entity `user`, id the name, changes `name` and `role`), `user.active` (`active`), `auth.login` (entity `user`; success has empty changes, a failed attempt has outcome `denied`, reason `invalid credentials` and the given name as actor), `project.create` (`name`, `public`), `project.member_add` (`member`, `role`; only when the role actually changed), `project.member_remove`, `project.archive` (`archived`), `project.import` (`issues`), `issue.create` (entity `issue`, id the issue key, changes `title`, `priority`, `assignee` and `labels`, each `[None or [], new]`), `issue.update` (changed title, description, priority), `issue.assign` (`assignee`), `issue.transition` (`status`, plus `resolution` when it changed), `label.add` and `label.remove` (`labels`: old and new sorted list), `comment.add` (`comment_id`), `comment.edit`, `comment.delete` (entity `issue`, the issue key). A denied entry has the action name of the refused operation (`issue.update` for any refused update, `issue.create`, `issue.transition`, `comment.add`, `label.add` or `label.remove`, `project.create`, `project.import`, ...), empty `changes` and the actor's name; operations that fail validation, name a disabled actor, or target objects the actor cannot see write nothing.

11. Import and export. `export_project(key, actor)` (managers and admins; else `PermissionDenied`) returns `{"format": "tracker-export", "version": 1, "project": {key, name, public, archived, created}, "members": [{"user", "role"}], "issues": [{"number", "title", "description", "status", "priority", "reporter", "assignee", "resolution", "created", "updated", "closed", "labels", "comments": [{"author", "body", "created", "edited"}]}]}` with issues ordered by number. `import_project(data, actor)` (admins only) creates the project from such a dict: issue numbers, timestamps, statuses, labels, comments and members are preserved, the next issue number continues after the highest imported number, and the result is the project dict. It is all-or-nothing: a dict that is not an export of this format (`ValidationError`), a project key that already exists (`Conflict`), users named in the data that do not exist (`ValidationError` naming them), or duplicate or invalid issue numbers (`ValidationError`) change nothing. `export_csv(key, actor, path)` writes the issues of a project as CSV with the header `key,title,status,priority,reporter,assignee,labels,created,updated` (labels joined with `|`, an empty assignee as an empty field) atomically and returns the number of issues. An exported project can be imported into a fresh tracker with the same users and then exports identically.

12. HTTP API. `tracker.api.make_server(tracker, host="127.0.0.1", port=0)` returns a server with the attribute `port`, `start()` (background thread; returns the server), `stop()` and the context-manager protocol. JSON in and out, `Content-Type: application/json` on every response, errors as `{"error": "<message>"}`. Routes: `GET /health` (open, `{"status": "ok"}`); `POST /login` `{"name", "password"}` -> `{"token"}` (401 on failure); with `Authorization: Bearer <token>` (otherwise 401 with `WWW-Authenticate: Bearer`): `POST /logout` (204), `GET /me`, `GET /projects` -> `{"items": [...]}`, `POST /projects` `{"key", "name", "public"}` (201 and a `Location` header), `GET /projects/KEY`, `POST /projects/KEY/members` `{"user", "role"}`, `DELETE /projects/KEY/members/NAME` (204), `GET /projects/KEY/stats`, `GET /projects/KEY/export`, `POST /projects/KEY/issues` `{"title", "description", "priority", "assignee", "labels"}` (201 and `Location: /issues/KEY-N`), `GET /issues?q=&limit=&offset=&sort=` (the search result), `GET /issues/KEY-N`, `PATCH /issues/KEY-N` (any of the four updatable fields), `POST /issues/KEY-N/transition` `{"status", "resolution"}`, `POST /issues/KEY-N/comments` `{"body"}` (201), `POST /issues/KEY-N/labels` `{"label"}`, `DELETE /issues/KEY-N/labels/LABEL`, `PATCH /comments/ID` `{"body"}`, `DELETE /comments/ID` (204), `GET /audit?action=&entity=&id=&actor=&outcome=&limit=` -> `{"items", "total"}`. Status codes: 401 `AuthError`, 403 `PermissionDenied`, 404 `NotFound` and unknown routes, 405 with an `Allow` header for a known route with another method, 409 `Conflict`, 422 `ValidationError`, 400 for a body that is not a JSON object (`invalid JSON` / `body must be a JSON object`) and for an invalid `limit` or `offset` query value (`invalid limit` / `invalid offset`), 413 for a body above 1048576 bytes. The checks run in this order: route (404), method (405), authentication (401), body (400/413), then the operation. The server handles requests in parallel and prints no logs.

13. Background maintenance. `Maintenance(tracker, close_after_days=14)` has `run_once()`, which in one transaction closes every issue that has been `resolved` and not updated for more than `close_after_days` days (state `closed`, `closed` and `updated` set to now, one audit entry per issue: action `issue.transition`, actor `system`, changes `{"status": ["resolved", "closed"]}`) and deletes the tokens that have expired (`expires <= now`; one audit entry `maintenance.purge_tokens`, entity `token`, actor `system`, changes `{"deleted": [0, n]}`, only if n > 0), then calls `check_integrity()` and returns `{"closed": [issue keys], "tokens_purged": n, "problems": [...]}`, also stored in `last_report` (and `runs` counts the runs). `check_integrity()` returns problem strings: `project KEY: next_number N is not above the highest issue number M`, `issue KEY-N: closed time and status disagree` (an issue is closed exactly when `closed` is set) and `the audit sequence has gaps`; it returns `[]` for healthy data. `start(interval=60.0)` runs `run_once` in a daemon thread immediately and then every `interval` seconds (returns the object; calling it again while running does nothing), an exception in a run is stored in `last_error` as `"<ExceptionClass>: <message>"` and does not stop the thread, and `stop()` stops it and waits.

14. Consistency and concurrency. 8 threads, each with its own `Tracker` on the same database file, creating 10 issues each in the same project produce the keys `KEY-1` to `KEY-80` exactly once, with a consistent project counter and an audit log without gaps. Concurrent comments, labels and transitions never corrupt the data (`check_integrity()` stays empty). A failed operation (permission, validation, conflict) leaves no partial change behind, including the issue counter.
