# Offline synchronisation engine

Build `syncer.py` in the root of the code directory: a small replication system in which several devices keep a key-value store in sync through one server, while they may be offline, change the same keys concurrently, and lose their connection in the middle of a transfer.
Python 3, standard library only, no network (the devices and the server run in one process; the connection is simulated by a `Link` object). Independent tests drive the API directly, inject connection failures and check that every device converges to the same data.
The central rule: the resulting data depends only on WHICH operations exist, never on the order or the number of times they were delivered.

## Requirements

1. Operations. All changes are operations, plain dicts with the keys `op_id` (str), `device` (str), `ts` (int, a Lamport timestamp, at least 1), `base` (int, at least 0, the number of the last server operation the device had seen when it created this one), `type` (`"set"`, `"delete"` or `"incr"`), `key` (non-empty str of at most 200 characters) and `value` (any JSON-serializable value for `set`, `None` for `delete`, a non-zero int, not a bool, for `incr`). The server adds the key `seq` when it stores an operation. A key is either a REGISTER (changed by `set`/`delete`) or a COUNTER (changed by `incr`); the first accepted operation on a key decides, and later operations of the other kind on it are rejected with the reason `"type mismatch"`. The module defines `ConnectionLost(ConnectionError)`.

2. The server. `SyncServer(path=None)` keeps an append-only log of accepted operations; `seq` numbers start at 1 and are assigned in the order of acceptance. `push(device_id, ops)` takes a list of operations and returns `{"accepted": [op ids], "duplicates": [op ids], "rejected": [{"op_id": ..., "reason": ...}], "latest_seq": n}`. An operation is rejected with the reason `"invalid operation"` if it is malformed (wrong types, missing keys, an `incr` value that is zero or not an int, a `delete` with a value, an empty key, `ts` below 1, ...) or if its `device` differs from `device_id`, and with `"type mismatch"` as described in 1. An operation whose `op_id` the server already holds (also from earlier in the same call) is a duplicate: it is reported as such and changes nothing. Accepted operations are stored in the given order and in one batch. `pull(since, limit=100)` returns `{"ops": [...], "latest_seq": n, "more": bool}` with the stored operations that have `seq > since`, oldest first, at most `limit` of them (copies carrying `seq`), and `more` true when further operations exist beyond this page. `latest_seq()` and `snapshot()` (see 3) complete the interface. All of it is safe to call from several threads.

3. Resolution. The state is a function of the SET of operations (duplicates and arrival order do not matter). For a register key the winner is the `set` or `delete` operation with the greatest pair `(ts, device)` (compared as a tuple: the timestamp first, then the device name as a string); if the winner is a `set` the key has its value, if it is a `delete` the key does not exist. For a counter key the value is the sum of all its `incr` values (a counter exists as soon as one `incr` was accepted, also when the sum is 0). `snapshot()` returns this state as a dict sorted by key. The module-level function `fold(ops)` computes the same state from any list of operations (it ignores repeated `op_id`s) and is what the server and the devices use.

4. The device. `Device(device_id, link, state_path=None)` is one replica (`device_id` is a non-empty str without `/`, otherwise `ValueError`). `set(key, value)`, `delete(key)` and `increment(key, n=1)` apply a local change at once and return the new `op_id`, which is `"<device_id>-<n>"` with `n` counting 1, 2, 3, ... per device. The operation gets `ts` = the device's Lamport clock after increasing it by 1, and `base` = the device's `last_seq`. Invalid input (empty or too long key, a value that is not JSON-serializable, a zero or non-int increment, using a counter key as register or the other way round according to everything the device knows) raises `ValueError` and changes nothing. A device is "offline" simply while it does not call `sync`; its changes wait in the outbox, `pending()` returns copies of them in order. `get(key, default=None)` and `items()` (a dict sorted by key) show the fold of everything the device knows (operations it received from the server, operations it pushed, and its pending ones), so a device always reads its own writes before syncing. The attributes `lamport`, `counter`, `last_seq`, `outbox`, `known` (a dict `op_id -> operation`) and `conflicts` hold the state.

5. Synchronisation. `device.sync(batch=50, page=50)` first pushes the outbox through `link.push(device_id, ops)` in chunks of at most `batch` operations (oldest first), moving every operation the server accepted or reported as duplicate out of the outbox into `known`, and dropping the rejected ones; then it pulls with `link.pull(last_seq, page)` repeatedly while `more` is true. The pull is incremental: it asks for operations after `last_seq` only, applies every received operation (also the device's own, which are simply already known: nothing is counted twice), sets `last_seq` to the `seq` of the last operation of a page, and raises the Lamport clock to the highest `ts` seen. It returns a `SyncReport` dataclass with the fields `completed` (bool), `pushed` (operations the server accepted), `pulled` (operations received), `duplicates`, `rejected` (list of the rejection dicts), `conflicts` (number of conflicts found during this sync) and `error` (the message of the connection failure or `None`). A second `sync` right after a complete one pushes and pulls nothing. The Lamport clock and the counter of own operations must also pick up own operations received after a restart without state file (so that new `op_id`s never repeat old ones).

6. Interrupted transfers. `Link(server)` is the connection: its methods `push(device_id, ops)` and `pull(since, limit=100)` call the server and count the calls in `link.calls`; `link.fail_next(n=1, where="request")` makes the next `n` calls raise `ConnectionLost`, with `where="request"` the server never receives the call, with `where="response"` the server handles the call and the answer is lost (any other `where` is a `ValueError`). A `ConnectionError` inside `sync` never propagates: `sync` stops, returns a report with `completed=False` and the message in `error`, and the device stays consistent and usable (operations whose acknowledgement was lost stay in the outbox and are sent again by the next sync, where the server reports them as duplicates and the device then drops them; the pull position only moves after a page was applied). However the failures are distributed, repeated syncs end with every device equal to the server snapshot, no operation lost and no counter incremented twice.

7. Conflicts. A conflict exists for a register key when a device receives a remote operation X (from another device) on that key and it has an own operation Y on the same key such that neither one had seen the other: `Y.base < X.seq` and `X.base < Y.seq` (an own operation that has not been accepted yet counts as having an infinitely large `seq`). The device appends to `device.conflicts` one dict per such pair, with the keys `key`, `local_op` (Y's id), `remote_op` (X's id), `winner_op` (the id of the register operation with the greatest `(ts, device)` among all it knows for that key, including X and Y) and `value` (the value that operation gives the key: its value, or `None` if it is a `delete`). The conflict is resolved automatically by rule 3; the list is only a record. Counters never conflict, a device never conflicts with itself, and operations on different keys or ones that did see each other (for example when a device first synced and then changed the key) are no conflict. `sync` counts the new conflicts in its report; `clear_conflicts()` empties the list and returns how many there were.

8. Persistence and restart. With a `state_path` the device writes its complete state (device id, Lamport clock, counter, `last_seq`, outbox, known operations, conflicts) atomically to that JSON file after every local change, every acknowledged push chunk and every applied pull page, and a new `Device` with the same path and id continues from it exactly (a file of another device id is a `ValueError`); so a device that is killed at any moment, even right after the server accepted a push whose answer never arrived, loses no change and duplicates none. `SyncServer(path)` appends every accepted batch to the file (one JSON object per line, flushed and synced) and rebuilds its log, its duplicate detection and the register/counter kinds from it when it is created again; a final line that is cut off by a crash is ignored. Many devices syncing in any order and any number of times, with or without failures, all converge to the server's snapshot once each of them has pushed everything and pulled everything.
