# Notes application, stage 5: users, ownership and sharing (amendment)

Everything required in stages 1 to 4 stays in force and its tests run again: the code written so far (store, search, SQLite, HTTP API, command line) must be extended, not rewritten, and existing data must keep working. Python 3, standard library only.

## Requirements

1. Users and tokens. `NoteStore.create_user(name, password)` creates a user and returns `{"name": name}`: names have 2 to 30 characters from letters, digits, `.`, `_`, `-` and start with a letter, are unique ignoring case and keep their spelling; passwords have at least 8 characters and are never stored in clear text (salted slow hash); anything invalid, or an existing name, is a `ValidationError`. `login(name, password)` returns a random token (at least 32 characters) valid for 24 hours of store-clock time; unknown user, wrong password and wrong types all raise `AuthError("invalid credentials")`. `user_for_token(token)` returns the user's name or raises `AuthError` (unknown or expired, expiry is exclusive: valid while `now < expires`); `logout(token)` invalidates it. The module defines `AuthError` and `PermissionDenied`, both subclasses of `NotesError`.

2. Ownership. Every note has the key `owner`: the name of the user who created it, or `None`. The methods `add`, `get`, `list`, `update`, `delete`, `search` and `tags` of `NoteStore` accept the keyword `actor` (a user name, default `None`). With `actor=None` nothing is restricted and a new note has no owner (the behaviour of stages 1 to 4). With an actor, `add` makes the actor the owner (an unknown actor raises `NotFound`); a note WITHOUT an owner belongs to everybody: every user may read, change and delete it (so data created before this stage stays usable).

3. Sharing. `share(note_id, user, mode, actor=None)` gives another existing user access to a note (`mode` is `"read"` or `"write"`, a second call changes the mode) and returns the list of the note's shares `[{"user", "mode"}]` sorted by user; `unshare(note_id, user, actor=None)` removes a share and returns the remaining list (`NotFound` if there was none); `shares(note_id, actor=None)` returns the list. Only the owner (or `actor=None`) may share, unshare or list shares. Sharing a note with its own owner or with an unknown user, or an invalid mode, is a `ValidationError` / `NotFound`. A note's shares disappear with the note.

4. Access rules with an actor. The owner may do everything. A user the note is shared with may read it (`get`, and it appears in `list`, `search` and `tags`), with `write` also `update` it, but never `delete` it, share it or change who it is shared with. A note the actor has no access to does not exist for them: `get`, `update`, `delete` raise `NotFound` exactly as for a missing id, and `list`, `search` and `tags(actor)` leave it out. A note the actor can see but not do an action on raises `PermissionDenied` (a message that names the actor and the note id). Refused operations change nothing.

5. HTTP. `make_server(store, host="127.0.0.1", port=0, auth=False)`: with `auth=False` the server behaves exactly as in stage 4 and the routes below do not exist (404). With `auth=True`: `POST /register` `{"name", "password"}` (open) returns `201 {"name"}`; `POST /login` (open) returns `200 {"token"}` (`401 {"error": "invalid credentials"}` on failure); every route except `/health`, `/register` and `/login` needs `Authorization: Bearer TOKEN` and answers `401 {"error": "unauthorized"}` with `WWW-Authenticate: Bearer` otherwise; `POST /logout` returns `204`; the note routes work as the actor of the token (creating notes owned by the user, listing and searching only what the user may read, `404` for invisible notes, `403 {"error": <message>}` for `PermissionDenied`); `GET /notes/ID/shares` returns `{"items": [...]}`, `POST /notes/ID/shares` `{"user", "mode"}` returns `200 {"items": [...]}`, `DELETE /notes/ID/shares/USER` returns `204`. A validation error is `422`. The order of the checks is: route, method, authentication, query parameters, body, the operation.

6. Existing data and the command line. A database created by stage 3 or 4 opens unchanged in content: the new tables and the owner column are added automatically on opening (the schema version stays `1`), its notes get `owner == None`, and everything continues to work. `export_json` keeps writing the stage 2 file format (notes without `owner`). New commands: `adduser NAME PASSWORD` prints `Added user NAME`; `share ID USER MODE` prints `Shared note ID with USER (MODE)`; `serve` takes the new flag `--auth`. The command line itself runs unrestricted (`actor=None`). An `AuthError` is exit status 2 with `Error: MESSAGE`, a `PermissionDenied` exit status 3 with `Error: MESSAGE`; all other statuses and outputs stay as before.
