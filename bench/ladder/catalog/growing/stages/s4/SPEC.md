# Notes application, stage 4: a local HTTP API (amendment)

Everything required in stages 1 to 3 stays in force and its tests run again. Add a local HTTP+JSON API on top of the existing `NoteStore`; do not duplicate the storage or validation logic (the API must use the store's own methods and errors). Python 3, standard library only (`http.server`), no network access beyond binding a local port.

## Requirements

1. Server object. `make_server(store, host="127.0.0.1", port=0)` (in `notes.py`) returns a server for the given `NoteStore` with the attribute `port` (the real port also when 0 was given), `start()` (serves in a background daemon thread and returns the server), `stop()` (stops and releases the port) and the context-manager protocol. Requests are handled in parallel (one thread per request) and no request log is printed. Every response, errors included, has `Content-Type: application/json` and a correct `Content-Length`; errors have the form `{"error": "<message>"}`. Connections are kept alive (HTTP/1.1).

2. Routes. `GET /health` returns `200 {"status": "ok"}`. `GET /notes` returns `200 {"items": [notes ordered by id], "total": N, "limit": L, "offset": O}`; the query parameters `limit` (integer 1 to 100, default 20) and `offset` (non-negative integer, default 0) page the list, and `tag` (repeatable, all given tags required) filters it; `total` counts the matches before paging. `GET /search?q=WORDS&tag=T` returns the same envelope with the notes found by `NoteStore.search` (an absent or empty `q` matches everything). `POST /notes` with a JSON object `{"title", "body", "tags"}` (body and tags optional) creates a note and returns `201` with the note and the header `Location: /notes/ID`. `GET /notes/ID` returns the note. `PUT /notes/ID` replaces the note's content: the object must contain `title`, and `body` and `tags` default to `""` and `[]` when absent; it returns the updated note. `DELETE /notes/ID` returns `204` with an empty body. A trailing slash on a path makes no difference.

3. Errors. Unknown paths and unknown note ids are `404` (`{"error": "no note with id N"}` for a missing note, `{"error": "not found"}` for a path); a known path with an unsupported method is `405` with an `Allow` header listing the allowed methods sorted and joined by `", "`; a validation error of the store is `422` with its message; an invalid `limit` or `offset` is `400` with `{"error": "invalid limit"}` or `{"error": "invalid offset"}` (limit is checked first); a request body of `POST` or `PUT` that is not valid JSON is `400 {"error": "invalid JSON"}`, one that is not a JSON object `400 {"error": "body must be a JSON object"}` (a missing body counts as the latter), and one larger than 1048576 bytes (judged by `Content-Length`, before it is read) is `413 {"error": "request too large"}`. The checks run in this order: route, method, query parameters, body, the operation itself.

4. Consistency with the rest. Changes made through the API and through the command line or another `NoteStore` on the same file are all visible to each other at once; concurrent requests (20 parallel `POST /notes`) lose nothing and produce distinct ids.

5. Command line. `serve [--host H] [--port N]` (defaults `127.0.0.1` and `8080`) prints the line `Serving on http://HOST:PORT` (with the real port, also for `--port 0`), flushes it, and serves the store named by `NOTES_FILE` until the process is terminated. All other commands behave as before.
