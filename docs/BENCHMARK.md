# Capability Ladder Benchmark

Measures what codebot (planner -> worker -> assertion runner -> recovery ladder) can build with the local model, on 12 projects of rising difficulty and on one project that grows over 8 stages. It runs the REAL harness; the benchmark only supplies the spec, the isolated workspace, the clock and the independent scoring. Code: `lib/codebot/capbench/`, catalog: `bench/ladder/catalog/`, results: `bench/results/ladder/` (git-ignored), trial workspaces `bench/runs/` and `projects/cap-*` (git-ignored).

All results in this file come from one laptop (i7-11375H, 15 GB RAM, RTX 3050 Ti 4 GB, thermally limited) and one model unless stated; they are
comparable with each other, not with other machines.

## Running it

```
codebot bench list                              the catalog (levels, tasks, requirements, reference plan available)
codebot bench run --level 3                     one level, 1 repeat
codebot bench run --suite ladder --repeats 3    levels 1-12, 3 clean trials each (--levels 1-6 selects a range)
codebot bench run --suite growing               the 8-stage notes project
codebot bench status [run]                      progress (also shows a dead runner)
codebot bench report [run] [--json|--history|--compare A B|--reclassify]
codebot bench resume [run]                      continue after a crash/reboot; finished trials and consumed task time are kept
codebot bench cancel [run]                      stop at the next poll
codebot bench validate [--levels 1-3|growing]   self-test of the catalog, no model
```

The menu (`codebot`, option `b`) wraps the same commands. Runs are detached and unattended; `codebot resume-all` (the systemd watchdog) resumes a benchmark whose runner died. ntfy messages go out for completion, a task timeout, a critical failure and a task that needs a human (interactive mode only), not for every step. Useful flags: `--task-minutes` (default 90), `--plan-minutes`, `--mode full|reference-plan|minimal|drafts`, `--interactive`, `--checkpoints` (score the hidden tests after every verified task), `--driver loop|engine`, `--seed`, `--model`, `--dry-run`, `--foreground`. Preflight refuses to start when Docker, the model server or disk space is missing, or when an exported variable (SANDBOX, WORKER_CMD, TASK_MAX_MINUTES ...) would change what is measured.

## The time rule

Each planned task has its own wall-clock budget (`TASK_MAX_MINUTES`, benchmark default 90). **There is no project-wide or suite-wide limit.** The budget belongs to the root task: `T3`, its split children `T3.1`, `T3.2`, and anything the worker adds while working on T3 draw from the same remaining budget, and retries or replans never reset it. Independent tasks each get their own budget. The clock starts when the worker starts the task and includes model inference, retries, tests and recovery; planning and setup are timed separately. The budget is persisted (`projects/<name>/taskclock.json`, heartbeat every 2 s), so a killed or rebooted run cannot get time back (it can lose at most one heartbeat). It is enforced: at expiry the worker process group and its sandbox containers are killed, the code is reset to the last verified checkpoint, the task is `timeout` and its dependents `skipped`; other independent tasks continue. Time spent waiting for the thermal guard counts toward the budget and is recorded separately (`thermal_s`). A timeout is recorded as `TIMEOUT`, never as an implementation failure. A task that blocks on an ambiguity is terminal (`BLOCKED_AMBIGUITY`) unless `--interactive`.

## Catalog

| level | project | main challenge |
|---|---|---|
| 1 | utility library | simple accuracy |
| 2 | config parser | interacting parsing rules |
| 3 | dependency resolver | algorithms |
| 4 | CLI task manager | multi-command app, persistence |
| 5 | debug an existing app (6 bugs) | diagnosis, no regressions |
| 6 | modular notes app | architecture across files |
| 7 | SQLite inventory | transactions, consistency |
| 8 | local REST API | multi-layer integration |
| 9 | background job system | concurrency, recovery |
| 10 | extend a ~1,900-line helpdesk codebase | modifying unfamiliar code |
| 11 | offline sync engine | distributed state, idempotency |
| 12 | issue tracker (14 requirements, many tasks) | long-horizon engineering |
| growing | notes app in 8 stages: storage, tags/search, SQLite, HTTP API, users/sharing, reminders + worker, multi-device sync, package refactor | evolving a project without regressions |

Every level has a versioned `manifest.json`, `SPEC.md`, `seed/`, a `reference_solution/`, **hidden `reference_tests/`** (hand-written, never shown to the worker, never generated by the model; they run on a copy of the workspace after the trial) and, for levels 1-12 and calc_go, a validated `reference_plan.json`. `codebot bench validate` proves the oracle: all reference tests pass on seed + solution, the bare seed does not pass (regression-flagged requirements excepted), and every requirement has tests. In the growing project each stage starts from the previous stage's final code, earlier requirements stay in force (earlier stages' frozen assertions become a regression-gate task, and the hidden tests of all earlier stages are scored cumulatively), and each stage is its own trial with its own per-task budgets.

## Two verification layers

The harness verifies each task with its own assertions (what the planner wrote, `internal`). The hidden tests are the `reference` layer. A task the harness accepted but the hidden tests reject is a **verification gap**; the report lists these separately from implementation failures.

## Metrics and failure categories

Project level: wall time, planning time, tasks planned/verified/timed out/blocked/skipped, hidden-test pass rate, requirements met, checkpoint curve, thermal time. Task level: time used and remaining, attempts, split/recovery steps, thermal wait, outcome. Model-call level: calls, prompt/generated tokens, inference seconds. Failure categories (`PLANNING_OMISSION`, `PLANNING_UNSOUND`, `IMPLEMENTATION_ERROR`, `VERIFICATION_GAP`, `RECOVERY_LOOP`, `CONTEXT_FAILURE`, `TIMEOUT`, `BLOCKED_AMBIGUITY`, `INFRASTRUCTURE_ERROR`) are assigned by heuristics from recorded evidence; the raw evidence stays in the trial directory and `report --reclassify` re-runs the classifier. Treat the labels as a first reading, not a verdict. Reports: `report.json`, `report.md`, `trials.csv`, `tasks.csv`, `calls.csv` in the run directory, `history.jsonl` across runs; a partial run is labelled `running`, not failed; the report names the ceiling (highest level held in every repeat).

## Diagnostic modes (never mixed into the normal score)

`--mode reference-plan` replaces the model's plan with the catalog's validated plan (isolates planning from implementation); `--mode minimal` runs a bare loop with one attempt and no recovery (isolates what the recovery ladder adds). The default `full` is the benchmark proper. Every report and every `history.jsonl` row carries the mode, so a diagnostic trial is never mistaken for a full one; compare only trials of the same mode.

`--mode drafts` measures drafts mode (`lib/codebot/drafts.py`, the workflow `codebot new` creates): no planner and no tasks; the model writes the whole program in rounds judged by the spec's own examples, with restarts, and the best version is delivered. `--task-minutes` is the time of the whole run (45 matches `bench/baselines/`), and the trial's repeat number picks the sampling seed (`DRAFTS_SEED = --seed + repeat - 1`, default seed 1), so `--repeats 2` replays the baselines' seeds 1 and 2. The trial records the delivered round and examples, the spec items without examples and the cut-off and unchanged replies (`report.md` column `examples`). The growing project is not available in this mode.

## Integrity

Specs, tests, scoring and results live outside the workspace and the Docker sandbox; the worker only sees its workspace. Trial workspaces are created fresh (`bench/runs/<trial>/code`) and a run never reuses one; a re-planned trial is destroyed and recreated. Each trial also gets a private, empty memory (`MEMORY_DIR=projects/<trial>/memory`: lessons and sizing stats), so trials are independent of each other and of your real projects, and a benchmark never changes the shared `memory/` the real agent uses. Lessons a worker saves during a trial carry over to later tasks of that same trial only. Data are versioned (`version` in each manifest, recorded with every trial).

## Known limits (read before quoting numbers)

- Classification of failures is heuristic. Timeout enforcement granularity is about 2 s. Suspend/hibernate time is not charged.
- The hidden tests need the Docker sandbox (preflight enforces it). Level 10's seed is 1,923 Python lines (target was 2,000-4,000). The planner emits at most `max_tasks` tasks per call (manifest `planner`); levels 10-12 and the growing stages stress this.
- Reference plans exist for levels 1-12 and calc_go; the growing project has none, so `--mode reference-plan` is unavailable there. The calc_go plan (2026-10-18) is hand-written: one task per requirement, each with the spec's own examples plus checks of every rule the requirement states, on inputs that differ from the hidden tests; standard error is checked through `python3 -c`.
- Interactive mode (`--interactive`, a blocked task waits for `codebot answer`) is covered by unit tests, not by a live run. The supervisor loop path is covered by the existing loop tests and one short real-model smoke run; no full 90-minute run, no full ladder and no growing run has been executed by the author of this framework. A full ladder with 3 repeats takes many days on this machine.
- Results from different models, seeds or `--task-minutes` values are not comparable; the report records all three.

## Smoke test on record (2026-10-15, ornith:9b, CPU, `codebot bench run --level 1 --task-minutes 4 --plan-minutes 10 --repeats 1`)

One trial through the real planner, bash supervisor, worker, assertion runner and hidden tests: plan 6.3 min (8 tasks, sound), coding 18.3 min, 6 of 8 tasks verified internally, 2 tasks hit the 4-minute budget and were recorded `TIMEOUT` (the other tasks continued), hidden tests 41/64 (64%), 3 `VERIFICATION_GAP` classifications (tasks the internal check accepted but the hidden tests reject), thermal pauses counted inside the budgets (0.0-0.7 min per task), CPU 85-94 C throughout. This proves the pipeline end to end with a shortened budget; it says nothing about the 90-minute capability numbers.

## First full-budget run (2026-10-15, ornith:9b, GPU auto-offload, `codebot bench run --level 1 --repeats 3`, run `20261015-180429-l1-full`)

90 min per task, 3 independent trials (private memory each), 5.4 h wall. Independent (hidden-test) pass rate per trial 78%, 47%, 73% (median 73%, below the 80% bar, so no level is held); internal verification 88%, 62%, 100%; 20/24 tasks verified; 0 timeouts (no task came near 90 min: max 48 min); 60 retries, 5 splits; CPU about 89 C mean, 96 C max.

What decided the score was the planner's assertions, not the time budget or the worker:
- Trial 2 lost two tasks to checks no code can pass: the planner wrote `slugify("", "expect")` and `safe_filename("", "expect")` (the schema key `expect` leaked into `args` whenever the expected value was an empty string), and the splitter wrote a `run` check with a stray `]` (a Python syntax error). The baseline guard accepted all three because they fail on the seed. Since 2026-10-16 the runner refuses such specs (a field name inside the inputs, `python3 -c` code that does not compile), so the guard rejects them as broken; not yet re-measured with the model.
- Weak checks: 7 VERIFICATION_GAP tasks. Trial 3 had a fully sound plan (0 unsound tasks in the reference audit) and verified 8/8, yet scored 73%: `slugify` 3/8, `truncate` 5/8, `safe_filename` 1/9 on hidden tests. Sound is not enough; the assertions cover only the spec's headline examples.
- Regressions, found on 2026-10-16 by re-scoring the hidden tests at the commit where each task passed: **23 of the 65 failed hidden tests were code that had worked and was broken by a later task** (trial 3: `safe_filename` 8/9 at T5, 1/9 after the T6 edit for `split_ext` in the same file left its `return` unreachable; trial 2: `clamp` 6/6 to 3/6, `is_valid_ipv4` 10/11 to 3/11; trial 1: `safe_filename` 7/9 to 1/9). Nothing re-ran earlier checks, so the report labelled these VERIFICATION_GAP. Without them the trials would have scored 88% / 63% / 84%. Fix: the regression gate (`REGRESSION_GATE=1`, default): a task counts as done only when every task already done still passes its check; otherwise the attempt fails and the worker is told which tasks it broke. Not yet re-measured.
- A 2026-10-16 attempt to raise coverage through the planner prompt (one assertion per stated rule, 4-12 per task) made ornith collapse the plan into one task in 5 of 6 first rounds; it was reverted.
- Splits rarely helped: children were often busywork ("create textutil.py with a docstring", "verify slugify still works") or contradicted the spec.
- The worker could do it: every function was solved in at least one trial (`truncate` verified in trial 3 after failing 13-14 attempts in trials 1 and 2).
