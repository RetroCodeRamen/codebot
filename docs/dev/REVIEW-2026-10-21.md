# Review: is codebot tuned to its benchmark or to the problem? (2026-10-21)

The user's question after a week of tuning against the same few tasks: has the harness been fitted to the tests themselves, or improved in
ways that hold for any project, with the tests only as the yardstick? Short answer: **the code is generic, but the evidence is not.** No rule
special-cases a task, yet every drafts-mode decision was made and measured on the same three tasks, so how much of it carries over is unknown.

## What holds up

- **No task is hard-coded.** `calc`, `calc_go`, `level_03`, `slugify` and the like appear in `lib/` only in comments, docstrings and the
  `check-spec` hint, as the evidence a rule was written from. No branch, constant or prompt depends on a benchmark task.
- **The hidden tests stay hidden.** They live outside every sandbox mount; the model never sees them, and drafts mode is judged only by the
  spec's own examples.
- **The big decisions are principled rather than fitted:** judge code by running it, never by the model's opinion of it; write the whole
  program and restart when stuck; keep the best version; take checks from the spec, not from the model. These came from the plain-loop
  baselines (2026-10-18) and match how the task pipeline failed (its model-written checks: 3 of 41 sound).
- **No dead code.** Every top-level function in `lib/` is used by production code (scanned 2026-10-21).
- **Backward compatibility is checked:** the last two parser changes left every recorded reply (428) and every catalog spec's examples (55 from
  21 specs) exactly as they were.

## Where it is fitted

1. **Development set = evaluation set.** Drafts mode has only ever run on level_01, level_03 and calc_go (14 runs plus the 3-hour series).
   Every rule was chosen on them and every number in the README comes from them. The other ten levels have never run.
2. **Ten of the twelve levels have no runnable examples** (levels 2 and 4-12: the specs are precise prose). Drafts mode has nothing to judge
   them by beyond "it builds", so its results there are untested and probably poor. That is a selection effect, not a bug: drafts mode was
   developed on the three tasks it could work on. `codebot check-spec` says so for any spec.
3. **Numbers fitted on small samples from those tasks,** all with ornith:9b, which is no longer this machine's model:
   `DRAFTS_PATIENCE=1` (13 runs), the reply cap of 3x the longest complete reply (10 runaway replies), `loop_watch`'s 8 lines / 2 repeats /
   at most 10% new lines (428 replies; its first version had to be corrected after it cut good code on the very next task, level_03), and the
   first prompt naming the files to write (calc_go writing README.md first). They are safety valves rather than the core loop, and the 30B
   model has not tripped any of them in 4 runs, but their values are fits, not facts.
4. **The example syntax follows how our specs are written.** "is / returns / raises / prints", and since 66ae7b8 "to standard error",
   "exits with status N", "with standard input". A spec that says "should output" is silently example-less; `check-spec` shows the count, which
   is the only guard.
5. **The task pipeline carries rules from the calc_go builds** (screening, rederive, `go run` exit statuses, one word per argument, stderr-only
   texts, the regression gate). Each rests on a general fact, but each was added to fix one task's failures, the pipeline still lost to drafts
   mode, and adding rules there was stopped on 2026-10-18. It is legacy now: kept so existing commands work, not developed further.
6. **The model was chosen on the same three tasks** (Qwen3-Coder-30B-A3B: 26, 26 and 75 hidden tests against ornith's 23, 21 and 64). The
   margin is large, but nothing outside those tasks has been run.
7. **My own process leaked task knowledge into one spec.** The improved calculator spec (`~/Documents/Development/calculator/SPEC.md`) adds
   examples for exactly the requirements whose hidden tests had failed. That is what a user would do after `check-spec` warns, but its results
   are not calc_go benchmark results and must never be reported as such.
8. **Single runs are coin flips, and a reasonable change can hurt.** The same model and seed built the original calculator spec in 5.5 minutes
   (15/15 examples; hidden 26/32). With the examples added for the three failing rules (24 examples, all holding on the reference solution),
   1 of 21 rounds compiled in 60 minutes and the delivered version passes 5 of 24 examples and 8/32 hidden tests: the model kept testing for
   infinity with `1/0`, which Go rejects at compile time, left imports and variables unused, and its repairs never found the lines. One seed;
   it says the change is not safe, not that it is bad.

## What to do (in order)

1. **Hold out tasks.** Treat level_01, level_03 and calc_go as regression checks only. Judge every future change on tasks never used for
   tuning: levels 2 and 4 with examples added the way `check-spec` asks a user to, and at least one brand-new spec of a different kind.
   A change that only helps the three tuning tasks is not kept.
2. **Several seeds per claim** (at least 3), as the 2026-10-18 baselines already showed.
3. **Spec examples are the lever** for the levels without them: the spec interview (the model proposes examples for each requirement that has
   none, the user accepts or fixes them) is the generic fix, not more harness rules.
4. **Feedback with context**: show the source line next to a compiler error (the `1/0` case above). Generic, but measure it on held-out runs
   before keeping it.
5. Leave the task pipeline as it is; mark it legacy in the docs.
6. Disk: the experiment data is local and git-ignored (about 85 GB, mostly models nobody uses now); what to delete is the user's call (list
   in the session report of 2026-10-21).
